## 3. Dockerfile.ollama

- **Stage `ollama`:** the pinned upstream image. It deletes every subdirectory of
  `/usr/lib/ollama`, then any dangling symlink, which leaves only the CPU files.
- **Stage `runtime`:**
  - pinned trixie-slim, plus the CA bundle copied from the pinned upstream stage.
    This changed during implementation: an `apt-get install ca-certificates` would
    not be pinned.
  - copies `/usr/bin/ollama` and `/usr/lib/ollama`
  - the ENV defaults from the brief: `OLLAMA_HOST=127.0.0.1:11434`, `OLLAMA_NO_CLOUD=1`,
    `OLLAMA_KEEP_ALIVE=30m`, `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_NUM_PARALLEL=1`,
    `OLLAMA_CONTEXT_LENGTH=8192`, `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE=q8_0`,
    `OLLAMA_DEBUG=0`
  - `ENTRYPOINT ["ollama"]`, `CMD ["serve"]`
  - nothing runs as root at runtime, and nothing writes to `/root` or a home directory
  - static labels `io.github.jmtovar.local-llm-images.accelerator=cpu` and
    `io.github.jmtovar.local-llm-images.arch=amd64` (see section 6)
- **Stage `base`:** `OLLAMA_MODELS=/models` (bind mount).
- **Stage `model`:**
  - Takes `ARG MODEL` and `ARG MODEL_DIGEST`, with `OLLAMA_MODELS=/opt/ollama/models`.
  - One `RUN` step:
    1. `ollama serve &` with `HOME=/tmp/ollama-build`, then wait until it answers
    2. `ollama pull "$MODEL"`
    3. check that `blobs/sha256-${MODEL_DIGEST#sha256:}` exists and hashes to
       `MODEL_DIGEST`, and that the stored manifest references it (`grep -F`). Either
       failure fails the build.
    4. stop the server and remove the temporary home
    5. `chmod -R a+rX`
- The workflow picks the target (`base` or `model`) for each matrix entry.
- `ARG OLLAMA_VERSION=0.40.2` (plain digits) is the single source of the Ollama version.
- Labels are covered in section 6.
- Read-only model directory (verified in the local test, 2026-10-11): with the
  directory `chmod -R a-w`, `ollama serve` starts, lists and runs the model with no
  prune or permission errors. **`OLLAMA_NOPRUNE` is not needed.**

## 4. Smoke test (every image, every run)

- **How images are built:** with buildx's `docker` driver and `load: true`, so they go
  straight into the runner's Docker and aren't stored twice.
- **The script:** `.github/scripts/smoke-test.sh <image> [ollama-model] [digest]`.
- **How the container runs:**
  - as `--user 65534:65534 --read-only`, with `HOME=/tmp` and a tmpfs `/tmp`
  - with `--network host`, so the runner can reach the server's localhost-only API
  - `base` gets a tmpfs at `/models` with `mode=1777`. Docker's default tmpfs is
    root-owned with mode 755, which failed the first CI run.
  - this mimics an unprivileged user running a read-only SIF
- **The test fails if:**
  1. `ldd` prints `not found` for `/usr/bin/ollama`, `/usr/lib/ollama/llama-server` or
     any `.so` under `/usr/lib/ollama`, or if no CPU library is present.
  2. `ollama serve &` doesn't answer `ollama list` within 60 s.
  3. `ollama --version` doesn't report the pinned version.
  4. `ollama list` fails. For model images it must also show the model, with an ID equal
     to the first 12 hex characters of the pinned digest.
  5. Any GPU library directory exists under `/usr/lib/ollama`: a name matching `cuda*`,
     `mlx_cuda*`, `vulkan*` or `rocm*`. In practice the test fails on *any*
     subdirectory there, since the CPU build has none.
  6. On the host side, `docker inspect` shows a label
     `io.github.jmtovar.local-llm-images.accelerator` other than `cpu`, or `.arch`
     other than `amd64`, or an image `Architecture` other than `amd64`.
  7. Model images only: one short prompt returns no text. The runner sends it with
     `curl --max-time 300` to `/api/generate`, using `"stream": false` and
     `"options": {"num_predict": 8}`. This takes the same HTTP path as `compare.sh`.
     The image itself has no curl; the runner's `curl` and `jq` are used.
     Text in `response` or `thinking` counts. Gemma 4 sometimes spends all 8 tokens on
     thinking, which failed one CI run with an empty `response`.
- **What happens afterwards:** only an image that passed is pushed. The push loops
  `docker push` over the metadata tags.

## 5. Branching and commits

- `main` is the release branch. It starts as the owner's empty root commit
  `c5c2641 init repo`.
- **No direct commits to `main`, ever.** Every change, including `.gitignore`, `README.md`
  and `CLAUDE.md`, goes on a `<type>/<short-description>` branch and reaches `main`
  through a PR.
- Branch types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `ci`
  (e.g. `feat/initial-scaffolding`, `fix/smoke-test-timeout`). Release branches are
  `chore/release-X.Y.Z`.
- Commits follow Conventional Commits: `<type>(<scope>): <summary>`, with the same
  types. Example scopes: `ollama`, `ci`, `scripts`, `readme`, `plans`, `bootstrap`.
- Commit type → version bump:

  | Commit | Bump |
  |---|---|
  | `<type>!:` or a `BREAKING CHANGE:` footer | MAJOR |
  | `feat` | MINOR |
  | `fix` | PATCH |
  | `docs`, `ci`, `chore`, `style`, `refactor`, `test` | PATCH, or no release |

  **Rule (decided):** the impact-based policy in section 6 decides the bump, and the
  commit type follows it. So an Ollama minor upgrade or new model weights is
  `feat(ollama): …` (MINOR), an Ollama patch upgrade is `fix(ollama): …` (PATCH), and
  renaming or removing an env default is `feat(ollama)!: …` (MAJOR).
- Each commit is a self-contained, testable change. Push after each commit so CI tests
  it. Squash the branch only when the owner asks.
- PRs are opened with `gh pr create --base main` and a clear description: summary, what
  changed, how it was verified, and anything left to do. Then stop and report that the
  PR is ready.
- **Never run `gh pr merge`.** The owner merges every PR into `main` in the browser.
- PR descriptions include `Closes #N` for the issue they resolve. The initial
  scaffolding PR uses `Closes #1`; issue #1 is "Initial scaffolding: Ollama images, CI
  workflow and bootstrap environment".
- No required status checks. The push runs on the PR's branch show on the PR.
- The fine-grained PAT needs these permissions on this repo only: Contents read/write,
  Pull requests read/write, Workflows read/write, Actions read, Issues read, Metadata
  read. Cancelling runs would need Actions read/write; that isn't needed.

## 6. Versioning (Semantic Versioning, digits only, never a `v` prefix)

- Releases are `X.Y.Z`. Prereleases are `X.Y.Z-alpha.N` or `X.Y.Z-beta.N`.
  The first release is `0.1.0`.
- One version covers the whole repo. The model goes in the image name and the version
  in the tag:
  - `ghcr.io/jmtovar/local_llm_images/ollama-base:<version>`
  - `ghcr.io/jmtovar/local_llm_images/ollama-ministral-3-3b:<version>`
  - `ghcr.io/jmtovar/local_llm_images/ollama-gemma4-e4b:<version>`
- Upstream versions that carry a `v` prefix are stored in our labels as plain digits.
- Bump policy:
  - **MAJOR:** a breaking change to how images are run: env defaults removed or
    renamed, paths changed, script arguments changed.
  - **MINOR:** a new model image, an Ollama minor upgrade, changed model weights, new
    features.
  - **PATCH:** fixes, an Ollama patch upgrade, docs, workflow changes that don't affect
    behaviour.

### Triggers

```yaml
on:
  push:
    branches: ['**']
    tags:
      - '[0-9]+.[0-9]+.[0-9]+'
      - '[0-9]+.[0-9]+.[0-9]+-alpha.[0-9]+'
      - '[0-9]+.[0-9]+.[0-9]+-beta.[0-9]+'
    paths:
      - Dockerfile.ollama
      - .github/scripts/smoke-test.sh
      - .github/workflows/ollama.yml
  workflow_dispatch:
```

- **Paths filter (decided):** branch pushes build the images only when one of the
  files above changes. Tag pushes and `workflow_dispatch` always build. GitHub doesn't
  evaluate path filters for tag pushes (verified in the workflow-syntax docs; see the
  sources in section 1).
  The `lint` workflow has no paths filter and runs on every push.
- The trade-off: a merge to `main` that touches only docs or scripts publishes no new
  `edge` or `sha-…` tag. So `edge` follows the image inputs, not every commit.

- In GitHub filter syntax, `+` means one or more of the preceding range, `.` and `-` are
  literal, and the pattern must match the whole tag.
- These do not trigger: `v0.1.0`, `0.1`, `0.2.0-rc.1`, `0.2.0-alpha`, `0.2.0-alpha.1.2`.
- Leading zeros can't be ruled out by a glob, so the gate job re-checks every tag
  against
  `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(-(alpha|beta)\.(0|[1-9][0-9]*))?$`.
- `'**'` matches every branch, including `main`; the gate job tells `main` apart from
  the others.
- There is no `pull_request` trigger. Branch push runs already show on the PR, and
  building multi-GB images twice would waste runner time.

### Gate job (every build job `needs` it)

1. It classifies the event into `kind`:

   | Event | `kind` | Publishes? |
   |---|---|---|
   | push to (or dispatch on) any branch except `main` | `test` | no |
   | push to `main` (or dispatch on main) | `edge` | yes |
   | tag `X.Y.Z-alpha.N` or `X.Y.Z-beta.N` | `prerelease` | yes |
   | tag `X.Y.Z` | `release` | yes |

   A tag that fails the strict regex fails the gate.
2. For a release only, it checks that the tagged commit is on main. It runs checkout
   with `fetch-depth: 0`, then:
   ```sh
   git fetch --no-tags origin main
   git merge-base --is-ancestor "$GITHUB_SHA" origin/main \
     || { echo "::error::Release tag $GITHUB_REF_NAME is not on main"; exit 1; }
   ```
3. For a release only, the newest version heading in CHANGELOG.md must be
   `## [X.Y.Z] - YYYY-MM-DD` and match the tag.
4. Prereleases get no main or CHANGELOG check. They may point at any branch.

### docker/metadata-action configuration

Every tag rule has an explicit `enable`, so no defaults are relied on:

```yaml
- id: meta
  uses: docker/metadata-action@dc802804100637a589fabce1cb79ff13a1411302  # v6.2.0
  with:
    images: ghcr.io/jmtovar/local_llm_images/ollama-${{ matrix.model }}
    flavor: |
      latest=false
    tags: |
      type=semver,pattern={{version}},enable=${{ needs.gate.outputs.kind == 'release' || needs.gate.outputs.kind == 'prerelease' }}
      type=semver,pattern={{major}}.{{minor}},enable=${{ needs.gate.outputs.kind == 'release' }}
      type=semver,pattern={{major}},enable=${{ needs.gate.outputs.kind == 'release' }}
      type=raw,value=latest,enable=${{ needs.gate.outputs.kind == 'release' }}
      type=edge,branch=main,enable=${{ needs.gate.outputs.kind == 'edge' }}
      type=sha,prefix=sha-,format=short,enable=${{ needs.gate.outputs.kind == 'edge' }}
    labels: |
      org.opencontainers.image.title=ollama-${{ matrix.model }}
      org.opencontainers.image.description=${{ matrix.description }}
```

- Each matrix entry carries its own one-line `description`. Setting it here overrides
  the description metadata-action would otherwise copy from the repo.
- The build platform is pinned explicitly: `platforms: linux/amd64` in
  `docker/build-push-action`, and the matrix runs only on `ubuntu-24.04` (x86-64)
  runners.

| Git event | Image tags published |
|---|---|
| push to any branch except `main` | none (build and smoke test only) |
| push to `main` | `edge`, `sha-<7 chars>` |
| tag `0.2.0-alpha.1` (any branch) | `0.2.0-alpha.1` only |
| tag `0.2.0-beta.2` (any branch) | `0.2.0-beta.2` only |
| tag `0.1.0` (must be on main) | `0.1.0`, `0.1`, `0`, `latest` |

- Images are also given a local-only tag, `local/ollama-<model>:smoke`, which the smoke
  test uses. It is never pushed.
- The push step runs only when `kind != test`.
- Builds use `provenance: false` and `sbom: false`, so `singularity pull` sees a plain
  manifest.
- There is no GHA layer cache, because multi-GB model layers would exceed the 10 GB
  per-repo cache limit (decided).
- If builds become too slow, the option is a GHCR registry cache: `cache-from` /
  `cache-to: type=registry,ref=…/ollama-<model>:buildcache,mode=max`. The trade-off is
  that every build, feature-branch runs included, would push that `:buildcache` tag to
  GHCR. The test-only branch builds would then no longer publish nothing, and a
  multi-GB cache would sit next to the images. It isn't used for now.
- The floating major tag `0` follows every 0.y release, which semver allows to break
  compatibility. The README notes this.

To read them: `singularity inspect --labels ollama-ministral-3-3b_0.1.0.sif`. That
works on both SingularityCE and Apptainer, which ships a `singularity` command.

## 7. Scripts

- **`scripts/run-server.sh <model> [version] [port]`**
  - `model` is one of `base`, `ministral-3-3b` or `gemma4-e4b`.
  - `version` is `X.Y.Z`, `X.Y.Z-alpha.N` or `X.Y.Z-beta.N`, checked with the strict
    regex. A `v` prefix is rejected with a hint.
  - Omitting `version`, or passing `latest`, resolves to the highest **release** on GHCR,
    via an anonymous token and `tags/list`. If offline, it falls back to the newest
    local SIF.
  - The default port is 11434.
  - The SIF is `${LLM_SIF_DIR}/ollama-<model>_<version>.sif`. `LLM_SIF_DIR` (and
    `LLM_MODELS_DIR` for `base`) are required, and the script stops with a clear message
    if they're unset.
  - It starts the instance `ollama-<model>` with
    `instance start --containall --cleanenv`, adding `--bind ${LLM_MODELS_DIR}:/models`
    for `base` only. The instance itself survives the script, because the runtime
    daemonises it.
  - It then launches the server detached, so it keeps running after the script exits
    and the terminal closes:
    ```sh
    setsid nohup "$SINGULARITY" exec --cleanenv --env "OLLAMA_HOST=127.0.0.1:$port" \
      "instance://ollama-$model" ollama serve \
      >"$log" 2>&1 </dev/null &
    ```
    The log goes to `~/llm-data/logs`. After launching, the script polls
    `http://127.0.0.1:<port>/api/version` and fails, showing the log tail, if the
    server doesn't answer.
  - `--cleanenv --env OLLAMA_HOST=…` go on the **exec**, not only on `instance start`.
    I believe a process exec'd into an instance takes its environment from the exec
    call plus the image, not from `instance start`; otherwise the image default
    `127.0.0.1:11434` would win. That belief is **unverified** and the laptop test
    below checks it.
  - Instance start plus exec is used because Docker-converted SIFs have no startscript
    (**unverified**, from memory).
  - It refuses to start if the instance is already running from a different SIF.
  - The runtime is `${SINGULARITY:-singularity}`.
- **Compatibility rule:** scripts and docs must work with both SingularityCE and
  Apptainer through the `singularity` command, using only flags both support. The
  planned set is `pull`, `inspect --labels`, `instance start`, `instance list`,
  `instance stop`, `exec`, `--containall`, `--cleanenv`, `--env`, `--env-file` and
  `--bind`. `instance list --json` is used only if both support it (**unverified**).
  Otherwise the scripts parse the plain output.
- **`scripts/stop-server.sh <model>`** stops the instance.
- **`scripts/compare.sh [-v VERSION] "prompt"`**
  - It makes sure Ministral is running on `${MINISTRAL_PORT:-11434}` and Gemma on
    `${GEMMA_PORT:-11435}`, both at the same version (default: the latest release). If
    either isn't running, it starts it with `run-server.sh`.
  - It errors out if they are running different versions.
  - It prints the version, then each answer with prompt-processing tokens/s, generation
    tokens/s and wall time. It needs `curl` and `jq`.
  - Running both side by side uses about 3 GB plus 6 GB of RAM, which fits in ~16-24 GB.

## 9. Conventions for every file

- **File header.** Every file I create gets a header in its own comment syntax:
  ```
  Generated by: <model name and version>
  Generation date: <YYYY-MM-DD>
  ```
  - `Last modified by` and `Last modified` are added only on significant later changes.
  - The header goes after the shebang in scripts, and after any `# syntax=` line in
    Dockerfiles.
  - Markdown, including README, CHANGELOG, CLAUDE.md and the plans, uses an HTML
    comment.
  - YAML, `.gitignore`, `.yamllint` and Modelfiles use `#`.
  - Formats without comments get no header. None are planned yet.
- **British English** in all prose: README, CHANGELOG, comments, commit and PR text.
  Upstream identifiers, spec keys, flags and env names stay exactly as upstream spells
  them (e.g. `org.opencontainers.image.licenses`, `llama-quantize`).
- **Brevity:** tight commit messages, PR bodies, CHANGELOG entries and comments.
- **Dates** are always ISO 8601.
