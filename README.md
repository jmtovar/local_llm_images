# local_llm_images

Container images for running a private, local LLM with [Ollama](https://ollama.com)
on a CPU-only Linux laptop, pulled and run with SingularityCE or Apptainer. GitHub
Actions builds the images and publishes them to GHCR. Conversations never leave the
machine.

| Image | Contents |
|---|---|
| `ghcr.io/jmtovar/local_llm_images/ollama-base` | Ollama only; models from a bind mount at `/models` |
| `ghcr.io/jmtovar/local_llm_images/ollama-ministral-3-3b` | Ollama + `ministral-3:3b-instruct-2512-q4_K_M` (2.8 GB) |
| `ghcr.io/jmtovar/local_llm_images/ollama-gemma4-e4b` | Ollama + `gemma4:e4b-it-q4_K_M` (6.1 GB) |

Tags are semver versions (`0.1.0`, `0.1`, `0`, `latest`); see [Versioning](#versioning).
All images are CPU-only and linux/amd64-only.

## Set-up

Everything uses the `singularity` command, which both SingularityCE and Apptainer
provide. Set `SINGULARITY=apptainer` to use that name instead.

Multi-GB pulls need scratch space, and the home disk is small, so point the cache and
temporary directories at the USB drive. Add this to `~/.bashrc` (`vim ~/.bashrc`):

```sh
export LLM_USB=/media/$USER/<usb-label>/llm      # adjust to your mount point
export SINGULARITY_CACHEDIR=$LLM_USB/cache
export SINGULARITY_TMPDIR=$LLM_USB/tmp
export LLM_SIF_DIR=$LLM_USB/sif                   # ollama-<model>_<version>.sif
export LLM_MODELS_DIR=$LLM_USB/models             # model store for the base image
mkdir -p "$SINGULARITY_CACHEDIR" "$SINGULARITY_TMPDIR" "$LLM_SIF_DIR" "$LLM_MODELS_DIR"
```

Apptainer may warn that the `SINGULARITY_*` names are legacy. The warning is
harmless, and keeping these names means the same set-up works on SingularityCE hosts.

The scripts need `curl` and `jq`.

## Running a model

```sh
scripts/run-server.sh ministral-3-3b          # newest release, port 11434
scripts/run-server.sh gemma4-e4b 0.1.0 11435  # a given version and port
scripts/run-server.sh base latest             # models from $LLM_MODELS_DIR
scripts/stop-server.sh ministral-3-3b
```

What `run-server.sh` does:

- It pulls `ollama-<model>_<version>.sif` into `$LLM_SIF_DIR` if it's missing.
  `latest` (the default) resolves to the highest `X.Y.Z` release on GHCR; prereleases
  are used only when named.
- It starts the instance `ollama-<model>` with `--containall --cleanenv`, then runs
  `ollama serve` inside it, detached from the terminal.
- The log goes to `~/llm-data/logs/ollama-<model>.log`.

To list models and chat from the terminal (pass the port the server uses):

```sh
singularity exec --cleanenv --env OLLAMA_HOST=127.0.0.1:11434 \
  instance://ollama-ministral-3-3b ollama list
singularity exec --cleanenv --env OLLAMA_HOST=127.0.0.1:11434 \
  instance://ollama-ministral-3-3b ollama run ministral-3:3b-instruct-2512-q4_K_M
```

Or use the HTTP API:

```sh
curl -s 127.0.0.1:11434/api/generate \
  -d '{"model": "ministral-3:3b-instruct-2512-q4_K_M", "prompt": "Hello", "stream": false}' | jq -r .response
```

To switch models, stop one and start the other. They can also run side by side, as
below.

**The `base` image** serves whatever is in `$LLM_MODELS_DIR`. To add a model, pull it
through the running server:
`singularity exec --cleanenv instance://ollama-base ollama pull <model>`.

## Side by side and comparing

**Run one model at a time.** Ministral and Gemma together take about 3 GB plus 6 GB
of weights plus context memory. On a machine with ~24 GB of RAM that is near the
limit: with both loaded, a desktop session can be pushed into swap.

```sh
scripts/run-server.sh ministral-3-3b 0.1.0 11434
scripts/run-server.sh gemma4-e4b 0.1.0 11435
scripts/compare.sh "Explain what a SIF file is in two sentences."
scripts/compare.sh -v 0.1.0 "…"
scripts/compare.sh -t "…"     # allow thinking (see below)
```

`compare.sh`:

- Starts both servers at the same version if they aren't running
  (`MINISTRAL_PORT`, default 11434; `GEMMA_PORT`, default 11435).
- Sends the prompt to each in turn and prints both answers with load time, prompt and
  output tokens/s, and wall time.
- Asks Ollama to unload each model after its answer (`keep_alive: 0`), so only one
  is in RAM at a time. The servers stay up. The cost is a reload of a few seconds per
  run.

**Thinking (Gemma 4).** Gemma 4 is a reasoning model. In Ollama 0.40.2, `/api/generate`
and `/api/chat` turn thinking **on by default** for models that support it. The
thinking text comes back in a separate `thinking` field, and its tokens count in
`eval_count`, so a short answer can cost hundreds of tokens. (The model may still
skip thinking on simple prompts, so one quick test can look as if it's off.)

- `compare.sh` sends `"think": false` by default, so output tokens are comparable.
- `-t` allows thinking; the thinking is printed separately, with an estimated token
  split.

To turn thinking off elsewhere:

- **API:** add `"think": false` to the request (accepted by every model; only
  `true` fails on models without thinking).
- **CLI:** `ollama run --think=false gemma4:e4b-it-q4_K_M`, or `/set nothink` inside
  a session.
- `--hidethinking` only **hides** the thinking: the tokens are still generated and
  still take time.

## Singularity hardening

- `--containall`: own PID, IPC and `/tmp`, and no host home. The container sees only
  what you bind.
- `--cleanenv`: host environment variables aren't passed in.
- Explicit `--bind`: only `/models` (base image), nothing else from the host.
- Secrets go in a `chmod 600` file passed with `--env-file`, never on the command line
  with `--env`, because command lines are visible to other users in `ps`.
  `run-server.sh` passes `OLLAMA_ENV_FILE` with `--env-file` if it's set.
- The server listens on `127.0.0.1` only.

## Data layout

- **USB drive** (public data; unencrypted is fine): SIF files, the Singularity cache and
  temporary files, and the base image's model store.
- **An encrypted location of your choice, e.g. `~/llm-data/`**: anything you create,
  such as chats, RAG data, the web UI database (later) and server logs.
- `ollama run` saves typed prompts to `~/.ollama/history`. Inside the containers,
  `--containall` makes that home temporary, so it's discarded when the instance stops.
  With an Ollama client installed on the host, set `OLLAMA_NOHISTORY=1` or keep the
  file in an encrypted location.

## Tuning

Defaults are baked into the images as `ENV` and can be overridden per server with an
env file (`OLLAMA_ENV_FILE=~/llm-data/ollama.env scripts/run-server.sh …`):

| Variable | Default | Reason |
|---|---|---|
| `OLLAMA_HOST` | `127.0.0.1:11434` | localhost only (`run-server.sh` sets the port) |
| `OLLAMA_NO_CLOUD` | `1` | disables Ollama cloud models and web search |
| `OLLAMA_KEEP_ALIVE` | `30m` | avoid slow reloads; `-1` = forever |
| `OLLAMA_MAX_LOADED_MODELS` | `1` | limited RAM/CPU |
| `OLLAMA_NUM_PARALLEL` | `1` | one user; parallel slots multiply context memory |
| `OLLAMA_CONTEXT_LENGTH` | `8192` | raise for long writing; costs RAM and speed |
| `OLLAMA_FLASH_ATTENTION` | `1` | required for KV cache quantisation |
| `OLLAMA_KV_CACHE_TYPE` | `q8_0` | about halves context memory; remove if quality drops |
| `OLLAMA_DEBUG` | `0` | `1` only for troubleshooting; debug logs may contain prompts |

On a laptop CPU, processing the prompt dominates. In a local test on a CPU-only laptop, Ministral processed
prompt tokens at about 16 tok/s and generated at about 6 tok/s. Keep interactive
context short. Put long-context work in cron jobs, where waiting doesn't matter.

Threads are a per-model `num_thread` parameter, not a server setting. Measure the number
of physical cores against the number of hardware threads.

Example Modelfiles:

- [`modelfiles/writer.Modelfile`](modelfiles/writer.Modelfile): higher temperature,
  16k context.
- [`modelfiles/cron.Modelfile`](modelfiles/cron.Modelfile): low temperature, 4k
  context.

`ollama create` writes to the model store, which is read-only in the model images.
Create presets on the `base` image (writable `$LLM_MODELS_DIR`). With a model image,
pass the same settings per request in `options`.

## Privacy checklist

- Never use `:cloud` model tags; keep `OLLAMA_NO_CLOUD=1`.
- Keep `OLLAMA_HOST` on `127.0.0.1`.
- Keep `OLLAMA_DEBUG=0`; debug logs may contain prompts.
- Check the base model of anything from Hugging Face before using it. This repo uses
  no Qwen or Qwen-derived models.
- Keep your own data under `~/llm-data/` in an encrypted location of your choice.

## Making the GHCR packages public

This is a one-time step after the first tag push, since a package only exists once an
image has been pushed to it. For each of `ollama-base`, `ollama-ministral-3-3b` and
`ollama-gemma4-e4b`: GitHub → your profile → **Packages** → the package →
**Package settings** → **Change visibility** → **Public**.

Alternatively, keep them private and pull with
`singularity pull --docker-login <file>.sif docker://ghcr.io/…`. It prompts for the
username and for a classic PAT with `read:packages` as the password, so nothing shows
in `ps`. `run-server.sh` doesn't do this, so pull the SIF by hand under the name it
expects (`ollama-<model>_<version>.sif`). Not yet tested on SingularityCE.

## Base image

- **Why Debian, not the official image:** the official `ollama/ollama` image is
  Ubuntu-based and carries about 3.5 GB of GPU libraries. These images are
  `debian:trixie-slim` with the Ollama binary and **only the CPU libraries** copied
  from the pinned upstream image.
  - Dropped: `cuda_v12/`, `cuda_v13/`, `mlx_cuda_v13/`, `vulkan/` and the dangling
    `include` link.
  - Kept: the 50 top-level files of `/usr/lib/ollama` (`libggml-cpu-*` variants,
    `llama-server`, etc.).
  - The CA bundle also comes from the pinned upstream image.
- **How it's verified:** every build is smoke-tested as an unprivileged user on a
  read-only root.
  - `ldd` must resolve every library.
  - No GPU directory may exist.
  - The `accelerator` and `arch` labels must be `cpu` and `amd64`.
  - `ollama serve`, `--version` and `list` must work.
  - Model images must list the pinned model and answer a short prompt.
- **CPU-only and linux/amd64-only.** Any GPU variant would get its own image name (e.g.
  `ollama-<model>-cuda`), so tags stay pure semver.
- **Model digests:** the build checks that the pulled manifest blob hashes to the pinned
  digest.

## Versioning

[Semantic Versioning](https://semver.org/spec/v2.0.0.html), **digits only, never a
`v` prefix**. One version covers the whole repo.

- Releases are `X.Y.Z`; prereleases are `X.Y.Z-alpha.N` or `X.Y.Z-beta.N`.
- Upstream versions with a `v` prefix are stored as plain digits in labels.

Bump policy (impact decides; the commit type follows it):

| Bump | When | Commit |
|---|---|---|
| MAJOR | breaking change to how images are run: env defaults removed or renamed, paths changed, script arguments changed | `<type>!:` or `BREAKING CHANGE:` footer |
| MINOR | new model image, Ollama minor upgrade, changed model weights, new features | `feat` |
| PATCH | fixes, Ollama patch upgrade, docs, workflow changes that don't affect behaviour | `fix`; `docs`/`ci`/`chore`/`style`/`refactor`/`test` are PATCH or no release |

Note on `0.x`: the floating tag `0` follows every `0.y` release, and semver allows
those to break compatibility. Pin `X.Y.Z` for anything that matters.

## Branching and releases

- `main` is the release branch. All changes go on `<type>/<short-description>` branches
  (`feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `ci`) and reach `main`
  through a pull request.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):
  `<type>(<scope>): <summary>`.

```sh
git switch -c feat/<short-description> main
# … commit, push; CI builds and smoke-tests without publishing
gh pr create --base main --fill   # description includes "Closes #N"
# merge in the browser
```

**Prerelease** (from any branch):

```sh
git tag -a 0.2.0-alpha.1 -m "0.2.0-alpha.1"
git push origin 0.2.0-alpha.1
```

Then note it under `## [Unreleased]` in CHANGELOG.md.

**Release** (only from `main`):

1. On `chore/release-X.Y.Z`, move the Unreleased entries under
   `## [X.Y.Z] - YYYY-MM-DD` and commit `chore(release): X.Y.Z`. Open a PR and merge
   it.
2. Then:
   ```sh
   git switch main && git pull
   git tag -a X.Y.Z -m "X.Y.Z"
   git push origin X.Y.Z
   ```

What each git event publishes:

| Git event | Image tags |
|---|---|
| push to any branch except `main` | none (build and smoke test only) |
| push to `main` | `edge`, `sha-<7 chars>` |
| tag `X.Y.Z-alpha.N` / `X.Y.Z-beta.N` (any branch) | that exact version only |
| tag `X.Y.Z` (must be on `main`) | `X.Y.Z`, `X.Y`, `X`, `latest` |

- Only tags matching `X.Y.Z`, `X.Y.Z-alpha.N` or `X.Y.Z-beta.N` trigger a build.
- Branch pushes rebuild images only when `Dockerfile.ollama`, the smoke test or the
  workflow changes; the lint workflow runs on every push.
- A release fails before building if the tag is not on `main`, if the newest
  CHANGELOG heading isn't `## [X.Y.Z] - …`, or if the tag isn't strict semver (e.g.
  `01.2.3`).

## Laptop checks

Run these after a new image version, to confirm what CI can't test (Singularity
itself). Use the version under test:

```sh
scripts/run-server.sh gemma4-e4b 0.1.0-alpha.1 11435
# (a) close this terminal; in a new one:
curl -s 127.0.0.1:11435/api/version
singularity instance list               # shows ollama-gemma4-e4b
# (b) the configured port is used, not the default:
ss -ltn | grep -E ':(11434|11435) '     # expect 11435 only
# (c) stopping stops the server:
scripts/stop-server.sh gemma4-e4b
curl -s 127.0.0.1:11435/api/version || echo "stopped"
```

Repeat with `ministral-3-3b` and `base`.
